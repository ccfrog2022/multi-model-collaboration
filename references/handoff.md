# 任务交接与上下文管理

交接服务于协调者组织的实现、独立测试与验收流程。重要任务在实现前增加方案审查，在测试后增加结果审查。任务阶段、调用、备份、库存和完成条件由项目公开命令执行。

## 准备派发材料

coordinator 先读取项目要求的规则与当前状态，再为本次角色准备必要材料：

| 角色 | 重点材料 |
|---|---|
| executor | 需求、接口、相关源码、精确写入路径、备份入口与验收条件 |
| tester | 独立验收依据、相关实现、边界场景、冻结测试及可复现环境 |
| reviewer | 被审方案或当前差异、对应摘要、相关源码、测试与原始证据 |
| probe | 具名工具、检查目的、只读范围与预期证据 |

项目必读规则按项目要求加载。其余资料围绕当前问题提供，短约束直接写明，长材料附可访问路径与版本。缺失关键材料时先明确缺口并补齐。

派发正文与工作实例回传使用英文，用户交付采用中文。避免为每次派发重新翻译和复制整段背景。

## 交接字段

任务输入包含：

- TaskId、本轮修订、Role、新的 InstanceId。
- 目标、真实授权引用、精确 AllowedPath / WritePaths、冻结测试。
- 最新 ExpectedDigest，以及该角色所需的 ExpectedPlanSha256 / ExpectedSubjectSha256。
- 验收项、本角色检查重点、必读材料与参考路径。
- 已有结果、新发现、待解决事项和本次交付要求。

revision 标识任务修复轮次，planRevision 标识所采用的方案修订。调用、测试与结果审查关联任务修订和当前文件摘要；方案审查关联方案修订与摘要。每次调用使用全新的 InstanceId，交接复用材料、产物与证据引用。

PrepareContext 将上述材料整理为对应角色的交接包，Invoke 使用 ContextId 进行版本核对。具体字段与示例见 [返工与角色上下文](iteration.md)。

## 收取结果

回传依次给出任务与调用身份、实际产物版本、改动、验证命令/退出码/结果、证据入口、待解决事项和下一步。

reviewer 另遵循项目规定的末行 COLLAB_VERDICT 协议。coordinator 阅读原始结果并通过 RecordReview、RecordAcceptance 和 Complete 登记审查、验收与完成。执行者的“完成”作为待验收交付处理。

多个实例通过各自调用 ID 关联证据。迟到或版本不符的报告保留在其原始任务记录中，当前验收使用满足当前摘要要求的证据。

## 修复与衔接

反馈给出位置、影响、复现或原始证据及验收条件；假设明确标为待验证。coordinator 将实施和测试修复分配给相应角色，保持原有职责独立性。

先读取 task.state、Revision 和实际差异。同一目标、范围与等级内的修复通过 Rework 进入新修订；方案需要调整时同时提供 PlanFile。目标、范围或等级改变时创建关联任务，引用前继的目标、产物与待解决项。

`Handoff` 用于 `handoff_required` 状态。当前修订的失败调用需要已完成文件范围、控制文件与进程清理检查；范围或清理等异常通过 RecoverTask 后采用完整 Rework。仍待接续的执行者失败使 Handoff 进入 implementing，由新的执行者接续；其余情况已有 accepted executor 或有效实现沿用记录时进入 validating，否则进入 implementing。coordinator 在 Reason 中说明已检查的失败与后续验证目标。

Handoff 保存交接前的调用、验收和审查 ID，并绑定失败调用原件摘要；当前验收设为 pending，真实流程验证和签署重新登记。仍待处理的失败由对应角色的新实例接续，reviewer 审查相同种类的对象。每次交接后取得当前文件的独立测试与新验收；重要任务还取得交接后的结果审查。完成门禁与下一轮实现沿用共同核对这些证据。

连续 Handoff 会核验并绑定此前失败的成功接续调用：执行者对应当前实现摘要，tester / probe 对应当前全部任务文件摘要，reviewer 对应相同 SubjectKind 的当前摘要。调用与结果原件、方案修订保持有效；reviewer 另绑定已登记的通过审查原件。交接摘要列出失败调用及保留的接续调用 ID，未接续项标为待处理。已有接续结果有效时继续使用；内容变化、证据失效或新的失败触发对应工作。原始失败记录持续保留，新边界后的独立测试、验收和重要任务结果审查照常完成。

交接重建、审查门禁和完成门禁共同核验既有失败绑定的原件、身份与摘要。历史记录缺失或损坏时，先恢复对应原件，再核验续作。

例如，执行者失败后已由新执行者完成，随后测试者失败：再次 Handoff 可保留该实现接续结果，安排新的测试者。若执行者又发生一次失败，则新的执行失败仍需要执行者接续。

续作满足当前验收、清理与审查条件后，直接 `Complete` 当前修订。尚未 Complete 时，发现需要另起修复轮次的具体问题才 `Rework`；例如审查 FAIL、需要修改实现或方案，或需要在新修订中补充测试。Reason 写明该问题与预期修复。已 Complete 后出现新问题时创建关联任务。Handoff 后再次发生普通调用失败，可重新检查并 Handoff；需要完整实施修复时采用默认 Rework。

审查 FAIL 使当前修订进入 blocked。Rework 检查清理、冻结测试和阻断项，保存旧轮次后开启修复。原方案有效时默认回到 implementing；只需验证或修正测试文件且符合实现沿用条件时，使用 ReuseImplementationFrom 进入 validating；更换方案时回到 planned，并重新取得重要任务的方案审查。

`RecoverLock` 核验进程退出后恢复遗留锁。清理未知、未决违规或 `failed_closed` 状态按 [异常恢复说明](recovery.md) 处理现场，通过 `RecoverTask` 核验恢复证据，再执行 `Rework`。原始失败记录与恢复证据分别保存。

Handoff 与 Rework 使用同一有效清理判断，历史调用已通过恢复核验时沿用其恢复证据。调用扫描中断后，以启动前基线重新核验文件范围；项目锁与恢复互斥的占用状态可在 Status 中分别查看。

Rework 将验收项设为 pending，并重置真实流程验证记录。新修订中的独立测试与验收使用当前 revision 和摘要，实现由本轮执行或经过核验的沿用调用提供，重要任务的结果审查也绑定当前修订；待验证项登记 pending，失败项登记 failed。

RecordAcceptance 将提交的文件保存为任务 `evidence/artifacts/` 下的独立副本，记录原始来源和摘要。记录中的 path、absolutePath 指向保存副本，sourcePath、sourceAbsolutePath 指向提交来源；历史引用始终使用对应副本。采用这种记录格式的固定路径测试报告可按任务范围重新生成，协调者检查后再次登记。旧修订或当前 Handoff 前的调用结果、已保存附件用于回顾；当前验收使用后续验证产物。

### 旧版证据继续使用

旧版验收记录的 path、absolutePath 直接指向提交时的报告文件。继续处理这些任务时：

1. 核对旧记录指向的文件与摘要，将该原件保留在原路径。另存备份可用于恢复；历史记录仍核验原路径。
2. 将当前验证报告输出到已授权的新文件路径，或任务的 worker inbox（默认 `collaboration-artifacts/<TaskId>/report-r2.txt`）。任务具名范围固定，需要新增测试写入路径时按任务范围规则安排；协调者可在任务 inbox 保存当前输出。
3. 完成当前修订或交接所需验证后，以新路径调用 `RecordAcceptance`。命令创建独立副本，旧记录和原件继续保留。

旧记录绑定的源路径在后续修订会被识别为历史证据，即使同名报告重新生成，也应使用上述新路径。新版独立副本格式的报告沿用正常更新与登记步骤。

交接只补充变化和当前所需材料。项目库存与控制快照按扫描配置核验，原件备份、版本绑定和独立验证继续执行。

## 提示词与本轮问题

派发描述本次角色应完成的整体结果：目标、验收依据、允许操作的范围、必须检查的行为，以及遇到哪些信息缺口需要回报。工作实例根据实际情况选择命令，完成相关工作与验证后一次回传可验收的结果。协调者在需要判断阶段、摘要或阻断原因时查询状态，使用已有结果安排下一步。

每个实际问题使用简短 ID，例如 F1；提供位置、影响、证据和预期行为。同一问题后续沿用原 ID。执行者或测试者在回传中标明已处理、仍待处理或存在异议，并给出依据；协调者把独立复验结果登记到现有审查或验收说明。问题清单直接放在派发与结果中，RecordReview 的 Findings 保存审查发现，运行时核对本次审查内 ID 非空且唯一。

回传先给出结果，再提供改动路径、检查命令与退出码、关键观察和证据入口。必要细节围绕失败、分歧和待决定事项展开。已通过的检查在相关内容变化、失败或证据冲突时再次执行。本轮验收满足且阻断问题关闭后交付；非阻断建议由协调者记录裁决或待办，不触发返工，后续新增目标按任务范围安排。

## 修复阈值与停止条件

协调者在现有问题清单与交接材料中，按同一问题 ID 记录尝试、验证证据和连续无进展轮数。一次针对该问题的修复尝试及其结果核验计一轮；尝试因工具或环境阻断而结束时，也记录该轮结果。轮次围绕问题累计，Handoff、Rework、更换模型或创建关联任务均延续原问题记录。

实质进展须有证据：原失败范围缩小、具体阻断条件解除，或获得支持不同修复方案的新诊断。仅修改文件、重述结论、更换模型或重复得到相同失败，不算实质进展。有实质进展时重新计算连续无进展轮数，并保留既有尝试记录。

**同一问题连续两轮无实质进展时，停止该问题相关的自动派发。** 完成该轮进程清理与证据保存，向用户说明问题 ID、两轮尝试及结果、当前阻断原因、继续所需条件和可选路径。后续按用户明确的继续指示恢复派发，并说明下一次尝试的依据与验证目标。未满足的验收项保持未通过。

非阻断建议记录裁决或待办，不触发 Rework 或额外修复派发。验收满足且阻断问题关闭后交付。阈值由协调者结合验证证据执行，记录使用现有问题清单与交接材料。

## 精简读取与记录

- 项目规则与稳定背景用权威路径引用；当前任务集中保存范围、验收和证据索引。
- 读取当前状态时优先提取 TaskId、state、锁、活动违规、清理标记、摘要和 Errors，完整输出保留可追溯入口。
- 命令和测试输出先返回退出码、关键结果与失败；遇到截断、解析异常或证据冲突时展开原件。
- 同一事实保留一个权威记录，其他总结引用它；必要的命令日志、备份和审查原件持续保存。

上下文精简围绕输入与转述进行，执行阶段及有效证据按项目命令契约核验。
